# TaskFlow Technical Architecture

Nov 17, 2026 · @Ashwini

TaskFlow is a React + Ant Design frontend talking to a modular NestJS API over MariaDB, served from one web address and built in vertical slices: each milestone delivers one working feature end to end. Approved on 18 November 2026, with all 22 decisions. The initialization decisions approved the same day also apply: one repository holding taskflow-backend, taskflow-frontend and taskflow-shared (in place of apps/ and packages/); Node.js 26 LTS; ES modules; and Vitest wherever this document says Jest. ## Gaps and risks found in the previous draft

Reviewing the first draft against the requirements turned up twelve problems. Each is fixed in this revision.

| # | Gap or risk | Why it matters | Fix |
| --- | --- | --- | --- |
| G1 | Where the frontend and API are hosted was never decided | If they end up on different sites, the browser silently stops sending the session cookie and login appears broken | Same origin \[D2\] |
| G2 | CSRF relied only on SameSite, CORS and JSON bodies | Those have known gaps; a cookie session needs a dedicated defence | Signed CSRF token \[D3\] |

## Backend

### NestJS building blocks

NestJS gives each kind of job its own building block. Knowing which block does what tells you where any piece of code belongs.

| Building block | Its job | In TaskFlow |
| --- | --- | --- |
| Module | Groups related parts and declares what other modules may use | `TasksModule` holds the tasks controller, service and repository, and exports the repository for `TrashModule` |
| Controller | Receives HTTP requests and returns responses. No business rules. | `TasksController` has `@Get()`, `@Post()`, `@Patch(':id')`, `@Delete(':id')` |
| Service | Business rules; knows nothing about HTTP | `TrashService.deletePermanently()` checks the task is in Trash before removing it |
| Entity | A class that describes one database table | `Task` with its columns, types and relation to `User` |
| Repository | All database queries for one entity, always scoped to a user | `TasksRepository.findActiveOwned(userId, id)` |
| DTO | A class that describes and validates one request or response | `CreateTaskDto` with `@IsNotEmpty() @MaxLength(100) title` |
| Guard | Decides whether a request may continue at all | `JwtAuthGuard` (logged in, current `tokenVersion`) and `CsrfGuard` |
| Pipe | Validates and converts incoming data | Global `ValidationPipe` for DTOs; `ParseUUIDPipe` for `:id` |
| Interceptor | Runs code before and after a handler | `LoggingInterceptor` records method, path, status, time and a request ID |
| Exception filter | Turns any thrown error into the response the client sees | `AllExceptionsFilter` returns the standard error shape and never a stack trace |
| Middleware | Runs first, before NestJS routing | `helmet` (security headers) and `cookie-parser` |
| Custom decorator | Small helper for repeated code | `@CurrentUser()` gives the logged-in user's ID; `@Public()` marks open endpoints |

### The order NestJS runs them

For every request: **middleware → guards → interceptors (before) → pipes → controller → service → repository → interceptors (after)**. If anything throws, the **exception filter** builds the response.

This order is why security sits where it does. Guards run before pipes, so an unauthenticated request is rejected (401) before its body is even read. Pipes run before the controller, so controllers only ever see valid data.

### Global setup

In `main.ts` and `AppModule`:

- Global prefix `api`, so every route starts with `/api`.
- `helmet()` and `cookie-parser` middleware.
- `JwtAuthGuard` then `CsrfGuard` as global guards (`APP_GUARD`). Auth runs first, so a logged-out request gets 401, not a CSRF error.
- Global `ValidationPipe` with `whitelist: true`, `forbidNonWhitelisted: true` and `transform: true`. Unknown fields such as `userId` in a body are rejected, not silently used.
- Global `AllExceptionsFilter` and `LoggingInterceptor`.
- Environment variables validated at startup; a missing secret stops the app immediately.

## Authentication security

The browser keeps the JWT in a cookie that JavaScript can't read. That protects the token from theft by malicious scripts, but it means the browser sends the cookie automatically, so we must also stop other websites from triggering requests with it. That is what CSRF protection is for.

### Session cookie

| Setting | Value | Why |
| --- | --- | --- |
| Name | `__Host-tf_session` in production, `tf_session` in development | The `__Host-` prefix makes the browser reject any version of this cookie set from a subdomain or without HTTPS, so it can't be overwritten |
| HttpOnly | Yes | JavaScript can't read it, so a script injected into the page can't steal the session |
| Secure | Yes in production | Only sent over HTTPS |
| SameSite | Lax | Not sent with requests that other sites make in the background. Still sent when the user clicks a link to TaskFlow, for example from an email. Strict would make those users look logged out on arrival. |
| Path | `/` | Whole app |
| Max-Age | 3,600 seconds | Matches the JWT's 1-hour expiry |

The JWT is signed with HS256 using a secret of at least 32 random bytes from an environment variable. It carries the user ID (`sub`), `tokenVersion` (`tv`), issue time and expiry. Verification accepts HS256 only, so a forged token can't switch to a weaker algorithm.

### CSRF protection \[D3\]

A cookie session is sent automatically by the browser, even on requests another website triggers. The CSRF token is a second value that only TaskFlow's own pages can read and send back.

#### The CSRF cookie

| Setting | Production | Development | Why |
| --- | --- | --- | --- |
| Name | `__Host-tf_csrf` | `tf_csrf` | `__Host-` makes the browser refuse the cookie unless it is Secure, has Path=/ and no Domain, so a subdomain can't plant or overwrite it |
| Secure | Yes | No (plain-HTTP localhost) | `__Host-` requires it |
| Path | `/` | `/` | Required by `__Host-` |
| Domain | Not set | Not set | Required by `__Host-` |
| HttpOnly | **No** | No | The frontend must read it to copy it into the header |
| SameSite | Lax | Lax | Same reasoning as the session cookie |
| Max-Age | Not set (ends with the browser session) | Not set | The token is re-issued whenever needed (rotation table below) |

Cookie names come from configuration, so the `__Host-` names are used wherever HTTPS is.

#### Token format

`<random>.<signature>`, both base64url:

- `random` = 32 bytes from Node's secure random generator.
- `signature` = HMAC-SHA256 with a dedicated `CSRF_SECRET` (at least 32 bytes, separate from the JWT secret) over `v1|<subject>|<random>`.
- `subject` = `user:<userId>:<tokenVersion>` for a logged-in user, or `anon` for a guest.

Binding the token to the user and `tokenVersion` means a token issued before login, or before a password reset, stops working afterwards.

#### What `CsrfGuard` checks

Only for POST, PATCH, PUT and DELETE; GET requests never change data and are never checked.

1. Both the cookie and the `X-CSRF-Token` header are present and at most 128 characters. Otherwise 403.
2. **Header equals cookie,** compared with `crypto.timingSafeEqual` after checking the lengths match. A normal `===` stops at the first different character, so its timing could leak how much of a guess was right.
3. Work out the expected subject: the user from a valid session, if any (on public routes the auth guard still reads the session, without requiring one); otherwise `anon`.
4. Recompute the HMAC for that subject and the token's `random` part, and compare it with the token's signature, again with `timingSafeEqual`.
5. Any failure: 403 `CSRF_INVALID`. The response never says which check failed.

The auth guard runs first, so a logged-out request to a protected route gets 401, not 403.

#### When the token changes

| Event | CSRF token |
| --- | --- |
| `GET /api/auth/csrf`, current token valid for the current subject | **Kept.** Returned unchanged, so several open tabs keep working |
| `GET /api/auth/csrf`, token missing, invalid or for another subject | New token for the current subject |
| Successful login | New token bound to the user |
| Logout | New `anon` token |
| Password reset completed | New `anon` token (all sessions are already invalid) |
| Session expires | The old user-bound token fails on the next unsafe request; the frontend fetches a new one and retries once |
| `CSRF_SECRET` changed in configuration | Every token fails once; each client fetches a new one automatically |

The frontend reads the cookie on every request rather than keeping a copy in memory, so all tabs pick up a rotated token immediately.

**Why this works:** another website can make the browser *send* TaskFlow's cookies, but it can't *read* them or add custom headers to cross-site requests. The signature means even an attacker who could plant a cookie can't make one the server accepts. Login and registration are covered too, which stops an attacker from silently logging you into *their* account.

### CORS

With one origin \[D2\], CORS stays **disabled**: browsers refuse to let other sites read TaskFlow's responses. The Vite proxy keeps development on one origin too. If a separate API domain is ever needed, CORS would allow exactly that one origin with credentials, and nothing else.

### Security headers

Set by `helmet` on API responses, and by the same rules on the server that delivers the frontend in production:

- **Content-Security-Policy:** scripts only from our own origin; no framing (`frame-ancestors 'none'`) to prevent clickjacking. Ant Design injects its styles at runtime, so styles need `'unsafe-inline'`; scripts never do.
- **Strict-Transport-Security** in production: browsers always use HTTPS.
- **X-Content-Type-Options: nosniff**.
- **Referrer-Policy: no-referrer** across the whole app (NFR-SEC-4).
- **Cache-Control: no-store** on API responses, so private task data isn't kept by shared caches or the Back button.

### What `JwtAuthGuard` checks

1. Skip if the route is marked `@Public()`.
2. Read the session cookie; verify signature, algorithm and expiry.
3. Load the user. Missing user or unverified email: 401.
4. Compare the token's `tv` with the user's `tokenVersion`. Different or missing: 401 (FR-AUTH-14).
5. Attach the user ID to the request for `@CurrentUser()`.

### Login, step by step

1. Lowercase the email \[D5\] and normalize the password to NFC \[D20\].
2. **Reserve an attempt** for this email + IP. If the limit is already reached: 429 `TOO_MANY_ATTEMPTS` with a `Retry-After` header (see Rate limiter).
3. If the password is longer than 72 bytes, it can't be anyone's real password: run a dummy bcrypt comparison for equal timing, then 401 `INVALID_CREDENTIALS` (R13).
4. Look up the user. If none, still run the dummy comparison (NFR-SEC-5), then 401 `INVALID_CREDENTIALS`.
5. Wrong password: 401 `INVALID_CREDENTIALS`. The reserved attempt stays counted as a failure.
6. Correct password but unverified: 403 `EMAIL_NOT_VERIFIED` (FR-AUTH-10). The reservation is released, because the password was right.
7. Success: clear this email + IP's failures, set the session cookie, issue a new CSRF token, return the user.

**Client IP behind a proxy:** in production, NestJS must be told how many proxies sit in front of it (Express's `trust proxy` setting). Otherwise every request appears to come from the proxy, and one attacker's failures would block everyone.

### Logout

`POST /api/auth/logout` clears the session cookie (same name and attributes, expired immediately) and issues a fresh CSRF token. The frontend wipes the RTK Query cache, so no data from the previous user remains in memory, and goes to `/login`.

As approved, logout does not change `tokenVersion`. A JWT copied before logout stays valid until it expires; this is listed under Limitations in Requirements v2.

### Password validation

#### The rules, precisely

| Rule | Exact meaning |
| --- | --- |
| At least 8 characters (approved) | Counted as Unicode characters (code points), so 😀 counts as one |
| At least one letter and one number (approved) | A letter is any Unicode letter, such as `a`, `é` or `த`; a number is any decimal digit \[D21\] |
| At most 72 bytes \[D11\] | Measured in **UTF-8 bytes**, not characters: `a` is 1 byte, `é` 2, `€` 3, 😀 4 |
| Normalization \[D20\] | The password is converted to Unicode NFC before checking and hashing, at registration, reset and login |
| Spaces | Kept exactly as typed; passwords are never trimmed |

**Why normalize:** some keyboards type `é` as one code point, others as `e` plus a separate accent mark. They look identical but are different bytes, so without normalization a password set on one device could fail on another.

#### One implementation, used by both sides

The check lives once in `packages/shared/src/validators.ts`:

```ts
export const PASSWORD_MIN_CHARS = 8;
export const PASSWORD_MAX_BYTES = 72;

const encoder = new TextEncoder();
export const utf8ByteLength = (value: string) => encoder.encode(value).length;
export const normalizePassword = (value: string) => value.normalize('NFC');

export type PasswordProblem = 'TOO_SHORT' | 'TOO_LONG' | 'NEEDS_LETTER' | 'NEEDS_NUMBER';

export function checkPassword(raw: string): PasswordProblem | null {
  const value = normalizePassword(raw);
  if ([...value].length < PASSWORD_MIN_CHARS) return 'TOO_SHORT';
  if (utf8ByteLength(value) > PASSWORD_MAX_BYTES) return 'TOO_LONG';
  if (!/\p{L}/u.test(value)) return 'NEEDS_LETTER';
  if (!/\p{Nd}/u.test(value)) return 'NEEDS_NUMBER';
  return null;
}
```

`TextEncoder` is built into browsers and Node.js, so no package is needed.

- **Backend (authoritative):** a custom class-validator decorator `@IsValidPassword()` calls `checkPassword` on `RegisterDto.password` and `ResetPasswordDto.newPassword`. The service hashes `normalizePassword(password)`. A request that skips the frontend is still rejected.
- **Frontend (helpful only):** the React Hook Form rule is `validate: (v) => { const p = checkPassword(v); return p ? PASSWORD_MESSAGES[p] : true; }`, with the messages also from `packages/shared`. Users see the same message the server would send, before submitting.
- **Login** only checks that a password is present, so it never reveals the rules. Over-length passwords are rejected as invalid credentials (login step 3).

#### Boundary tests

One shared list of cases runs in both the backend and frontend test suites, so both sides must agree on every case.

| Password | Characters | UTF-8 bytes | Expected |
| --- | --- | --- | --- |
| `abcdefg1` | 8 | 8 | Valid |
| `abcdef1` | 7 | 7 | `TOO_SHORT` |
| `a1` + 70 × `x` | 72 | 72 | Valid |
| `a1` + 71 × `x` | 73 | 73 | `TOO_LONG` |
| `a1` + 35 × `é` | 37 | 72 | Valid |
| `a1` + 36 × `é` | 38 | 74 | `TOO_LONG` (only 38 characters, but too many bytes) |
| `a1` + 23 × `€` + `x` | 26 | 72 | Valid |
| `a1` + 24 × `€` | 26 | 74 | `TOO_LONG` |

API end-to-end tests add:

- Register with `é` typed as one code point, log in with `e` plus an accent mark: login succeeds (normalization).
- Log in with the real password plus extra characters beyond 72 bytes: 401, even though bcrypt alone would have matched (R13).
- Over-length password in register and reset: 400 with the `TOO_LONG` message; nothing is saved.

### Keeping tokens out of logs and the address bar

A raw verification or reset token should exist in only two places: the email in the user's inbox, and memory while a request is being handled. The database stores only its hash.

#### Logging rules

| Possible leak | Rule |
| --- | --- |
| URLs and query strings | Tokens are never in URLs by design \[D18\]. The request log records the **route pattern** (`/api/tasks/:id`), method, status, duration and request ID, never the raw URL or query string. Search text is personal data too. |
| Request bodies | Never logged, at any level, in any environment. |
| Headers | `Cookie`, `Set-Cookie`, `Authorization` and `X-CSRF-Token` are never logged. |
| Validation errors | The validation pipe is configured with `validationError: { target: false, value: false }`, so class-validator never attaches the submitted value. Field messages never repeat what was typed. |
| Error logs | The exception filter logs request ID, error type, message and stack, never the request. Database errors log only the driver code (for example `ER_DUP_ENTRY`), because MariaDB error messages can contain the submitted value. |
| SQL and debug logs | TypeORM query logging is off by default. In development, a small custom TypeORM logger prints SQL text **without parameter values**. Nodemailer's own logging and debug output are off. |
| Email links | `MailService` logs template name, user ID and the provider's message ID only, never the recipient, body or link. The link is built in memory and handed straight to the mail transport. |
| Redux in the browser | RTK Query keeps each mutation's arguments, including passwords and tokens, in the Redux store (R14). Login, register, verify and reset mutations call `reset()` as soon as they settle, and Redux DevTools are enabled only in development. |
| Postman | The shared collection never contains real tokens or passwords; values live in local environment variables. |

**Safety net:** every structured log entry passes through a `redact()` helper that replaces the values of these keys, at any depth, with `[REDACTED]`: `password`, `newPassword`, `token`, `csrfToken`, `tokenHash`, `passwordHash`, `authorization`, `cookie`, `set-cookie`, `x-csrf-token`. The rules above prevent leaks; the helper catches mistakes.

**Tests:** API end-to-end tests replace the log output with an in-memory sink, then run register, verify, resend, forgot and reset, including failures (invalid token, validation error, forced database error). They assert that no raw token, password, CSRF value or token hash appears in any captured line.

#### Removing the token from the address bar

On `/verify-email` and `/reset-password`:

1. Read `window.location.hash` once, when the page first loads.
2. **Immediately** call `history.replaceState(history.state, '', location.pathname)`. This removes the fragment from the address bar and from the current history entry, without reloading, before any request is sent.
3. Keep the token only in the component (a `useRef`). Never put it in the URL, Redux state or browser storage.
4. After success, navigate away.

One consequence: refreshing the reset page after the token is cleared leaves nothing to submit. The page then shows "This link has already been opened. Request a new link," with a button to do so. That's the safe trade-off.

A component test checks that after the page loads, the address bar has no fragment and `replaceState` ran before the API call.

### Rate limiter \[D9\]

#### The approved limits

| Limit | Key | Window | When exceeded |
| --- | --- | --- | --- |
| Failed logins | `login:<email>:<ip>` | 5 failures in any 15 minutes, then a 15-minute block | 429 with `Retry-After` |
| Resend verification | `resend:<email>` | 3 requests in any hour | Normal generic 200; no email sent |
| Forgot password | `forgot:<email>` | 3 requests in any hour | Normal generic 200; no email sent |

Emails in keys are already lowercased, so `A@x.com` and `a@x.com` share a count. Login failures for emails that don't exist count too, so the limiter behaves the same either way.

#### How it works

Each key holds a short list of timestamps (at most 5 for login, 3 for the others) and, for login, a `blockedUntil` time. This is a **sliding window**: "5 failures in any 15 minutes" is checked exactly, unlike a fixed window that resets on the clock and would allow up to 9 failures across a boundary.

**Simultaneous requests (R15).** Node.js runs our code on one thread, so a single synchronous step can't be interrupted. But login has a slow `await` in the middle: the bcrypt check. If we checked the limit before bcrypt and recorded the failure after, 20 parallel wrong-password requests could all pass the check first. So the limiter **reserves** an attempt in the same synchronous step as the check:

1. `tryReserve(key)`: drop timestamps older than the window; if blocked or full, refuse; otherwise add a timestamp now. No `await` happens inside this step.
2. Run the password check.
3. Wrong password: keep the timestamp. If it was the fifth, set `blockedUntil` 15 minutes ahead.
4. Correct password: `clear(key)`. Unverified: `release(key)` removes just this reservation.

Of 20 parallel attempts, exactly 5 reach the password check; the rest get 429.

**Expired entries.** Old timestamps are dropped whenever a key is used. A sweep every 5 minutes (a timer that doesn't keep the process alive on shutdown) deletes keys with no recent timestamps and no active block.

**Memory growth.** An attacker could try thousands of random emails to create many keys. Each key takes roughly 200 bytes, and the store is capped at **100,000 keys** (about 20 MB). When the cap is reached, a sweep runs first; if the store is still full, the oldest keys are dropped and a warning is logged. Dropping a key can only make that one key's limit more lenient, never block someone wrongly.

**Limits of an in-memory store** (accepted in NFR-SCALE-1): counts reset when the server restarts and aren't shared between servers. The store sits behind a `RateLimitStore` interface, so a Redis version can replace it later. The client IP comes from the request only after `trust proxy` is set correctly (see Login).

The clock is injected, so tests can move time forward instead of waiting.

#### Tests

| Scenario | Expected |
| --- | --- |
| 4 failures, then correct password | Logged in; count cleared |
| 5 failures, then a 6th attempt with the **correct** password | 429 with `Retry-After` about 900 seconds (AC-02.5) |
| Block reaches 15 minutes | Next attempt is checked normally |
| 5 failures spread 4 minutes apart (16 minutes total) | Not blocked: the first failure has left the window |

The first eleven run as API end-to-end tests with an injected clock; the cap and sweep cases are unit tests.

### Date-only values

A due date is a calendar day, like a date written on paper. It has no time and no time zone. The danger is JavaScript's `Date`, which always means a precise instant. Turning `2026-11-17` into a `Date` gives midnight in *some* time zone, and reading it back in another time zone can produce `2026-11-16`.

**The rule: a due date is a `'YYYY-MM-DD'` string from the form to the database and back. It never becomes a JavaScript `Date` on the server.**

#### How each layer keeps it a string

| Layer | What happens |
| --- | --- |
| API request | The DTO accepts only a strict `YYYY-MM-DD` string and checks it is a real calendar day by its numbers (no `Date` parsing). `2026-02-30` and `2026-11-17T00:00:00Z` are rejected. |
| Saving | The repository passes the string to TypeORM. For a `date` column TypeORM leaves a string unchanged, so `mysql2` sends `'2026-11-17'` and MariaDB stores that day. |
| Reading | **Without** `dateStrings`, `mysql2` would turn the `DATE` into a JavaScript `Date` at midnight in the connection's time zone, and converting it back could land on the previous day, depending on the server's time zone. **With** `dateStrings: ['DATE']`, `mysql2` returns the text `'2026-11-17'` as-is, and no `Date` is ever created. |
| Overdue | SQL compares `dueDate < :today` where `today` is the `'YYYY-MM-DD'` string from the client \[D16\]. MariaDB compares two dates; nothing is converted. |
| API response | `"dueDate": "2026-11-17"` |
| Frontend | `dayjs(value, 'YYYY-MM-DD')` for the date picker and display; `.format('YYYY-MM-DD')` when saving. Never `new Date('2026-11-17')`: JavaScript reads that as UTC midnight, which shows as the 16th anywhere west of UTC. |

The server process also runs with `TZ=UTC` as a second guard, but correctness doesn't depend on it.

#### Tests

- **Integration, repeated under three server time zones.** CI runs the date tests with `TZ=UTC`, `TZ=Asia/Kolkata` and `TZ=America/Los_Angeles`, deliberately overriding the usual UTC setting to prove `dateStrings` alone is enough. Each run saves and reads back `2026-11-17`, `2026-01-01`, `2024-02-29` (leap day) and `2026-03-08` (a daylight-saving change in the US), through the repository and through a raw query. Each must come back as the identical string, of type string.
- **Overdue boundary:** due `2026-11-17` is not overdue when `today` is `2026-11-17`, and is overdue when `today` is `2026-11-18`.
- **API end-to-end:** create a task with `dueDate: '2026-11-17'`; the read returns exactly that. `2026-02-30`, `17-11-2026` and a full timestamp each get 400.
- **Frontend unit:** the date-picker conversion helpers round-trip the same dates with Jest running under `Asia/Kolkata` and `America/Los_Angeles`.

### Indexes, checked against the actual queries

An index is a sorted copy of some columns that lets MariaDB jump straight to matching rows. It helps only when the query's conditions and sort order line up with the index's column order, left to right. One detail matters below: **InnoDB silently appends the primary key (`id`) to the end of every secondary index**, so an index on (`userId`, `deletedAt`, `createdAt`) is really ordered by (`userId`, `deletedAt`, `createdAt`, `id`).

#### Your Trash question

You were right to question it. The previous draft sorted Trash by `deletedAt DESC, id DESC`, but the index is ordered (`deletedAt`, `createdAt`, `id`). Because `createdAt` sits between them, two tasks deleted in the same millisecond could not be ordered by `id` straight from the index, so MariaDB would add a sort step.

The fix is to make the tie-breakers match the index: **Trash is sorted by `deletedAt DESC, createdAt DESC, id DESC`**. Within one user's trashed range, the index is already in exactly that order, so MariaDB reads it backwards with no sort. Users still see newest-deleted first, as FR-TASK-7 requires.

#### How the plans are verified

Tiny test tables mislead the optimizer: with 10 rows, reading the whole table is cheapest, so plans only mean something on realistic data. In M5 and M6, each query above is run with `EXPLAIN` and with MariaDB's `ANALYZE FORMAT=JSON` (which reports rows actually examined and time taken) against the performance dataset. The results are saved in `docs/db/query-plans.md`. A plan is accepted when it uses the expected index and examines no more than the user's own rows. Turning these checks into automated assertions is optional, listed under later improvements.

### Migrations

- Generated with the TypeORM CLI from entity changes, **read before committing**, and committed to Git.
- Applied with `migration:run` on deployment and before every test run.
- **MariaDB can't roll back schema changes inside a transaction.** If a migration with several steps fails halfway, the earlier steps stay applied. So each migration makes one logical change and has a working `down` method.
- The schema drift check in CI keeps entities and migrations in agreement.
- Seed data lives in a separate script, never in migrations.

### Transactions and token issuance

#### Issuing a token: one row per user and type (R3)

**Why "delete old, then insert new" isn't enough:** two resend requests, A and B, arrive together. Each runs in its own transaction and deletes the user's unused tokens. Neither can see the other's not-yet-committed insert, so neither deletes it. Both insert, and the user ends up with two valid links.

**The fix: let the database make two valid tokens impossible.** `auth_tokens` has a unique key on (`userId`, `type`), so it can hold at most one token of each type per user. Issuing a token is one atomic statement that inserts the row, or replaces it if one exists:

```sql
INSERT INTO auth_tokens (id, userId, type, tokenHash, expiresAt, usedAt, createdAt)
VALUES (?, ?, ?, ?, NOW(3) + INTERVAL 30 MINUTE, NULL, NOW(3))
ON DUPLICATE KEY UPDATE
  tokenHash = VALUES(tokenHash),
  expiresAt = VALUES(expiresAt),
  usedAt    = NULL,
  createdAt = VALUES(createdAt);
```

`TokensRepository.issue()` produces this through TypeORM's insert-or-update support.

**The locking that makes it safe:** InnoDB locks the (`userId`, `type`) key entry for the duration of the statement. If A and B run at the same moment, one waits for the other. The one that runs second overwrites the first. The **last write wins**, and its token is the only one that exists. The first token's hash is gone, so its link now reports "invalid" (AC-15.6). No explicit transaction or extra lock is needed, because one statement is already atomic.

Both requests still send an email, each after its own statement completes. Emails can occasionally arrive out of order; the older-looking one then says "This link is no longer valid, request a new one". That's acceptable and matches the approved rule that only the newest link works.

At registration, creating the user and issuing the verification token run in one transaction, so a new user never exists without a token.

#### Using a token: claim it in one statement (G3)

```sql
UPDATE auth_tokens SET usedAt = NOW(3)
WHERE tokenHash = ? AND type = ? AND usedAt IS NULL AND expiresAt > NOW(3);
```

If it changes one row, the token was valid and is now used. If it changes none, the service looks the hash up to tell the user why: not found (invalid or replaced), already used, or expired. Two simultaneous submissions can't both change the row, so only one succeeds.

#### Password reset (FR-AUTH-13)

1. **Before** the transaction: normalize and hash the new password. bcrypt is deliberately slow, and slow work inside a transaction holds locks longer.
2. **In one transaction**, through the transaction runner (see Repositories):
   - Claim the reset token. If no row changed, roll back and return the reason.
   - Update the user: new hash, `tokenVersion = tokenVersion + 1`, `passwordChangedAt = NOW(3)`, and `emailVerifiedAt = COALESCE(emailVerifiedAt, NOW(3))`.
3. **After commit:** send the "password changed" email and issue a new anonymous CSRF token. A failed email is logged; the reset stands.

Email verification follows the same pattern: claim, then set `emailVerifiedAt` if it's empty.

**Deadlock safety:** every transaction touches rows in the same order (token, then user), which prevents two transactions from waiting on each other. If MariaDB still reports a deadlock, the transaction runner retries the whole transaction once.

**Isolation level:** MariaDB's default, REPEATABLE READ, is fine because every critical step is a single conditional statement rather than a read followed by a separate write.

#### Concurrency tests

| Scenario | Expected |
| --- | --- |
| 10 resend requests in parallel for one user | Exactly one verification row; only the last-issued link verifies; the others report invalid |
| 10 forgot-password requests in parallel | Exactly one reset row; same outcome |
| A new link issued while an old one is being used | The old link is either already claimed (it succeeds) or replaced (it reports invalid), never both valid |
| Two parallel reset submissions with one token | One 204, one 400; `tokenVersion` rises by exactly 1 |
| Forced failure after the claim, inside the transaction | Rolled back: token still unused, password and `tokenVersion` unchanged (AC-17.11) |

## Repositories

**The rule: every database query lives in a repository.** Controllers call services; services and scheduled jobs call repositories; only repositories talk to TypeORM. Each SQL query then has exactly one home, where its ownership filter, index use and tests can be checked.

### The three repositories

| Repository | Methods |
| --- | --- |
| `UsersRepository` | `create`, `findById`, `findByEmail`, `markVerified`, `applyPasswordReset`, `deleteUnverifiedOlderThan(days, batchSize)` |
| `TasksRepository` | `create(userId, …)`, `findActiveOwned`, `listActive`, `update(userId, id, …)`, `moveToTrash`, `listTrash`, `findTrashedOwned`, `restore`, `deletePermanently`, `emptyTrash`, `countForDashboard(userId, today)`, `purgeTrashedOlderThan(days, batchSize)` |
| `TokensRepository` (new) | `issue(userId, type, tokenHash)`, `claim(tokenHash, type)`, `findByHash(tokenHash, type)`, `deleteExpiredOlderThan(days, batchSize)` |

Every `TasksRepository` method that serves a user takes `userId` first (see Task ownership). The cleanup job calls the three `…OlderThan` methods; it contains no SQL of its own.

### Transactions without leaking the database into services

Some operations need several repository calls to succeed or fail together. A small `TransactionRunner` in `DatabaseModule` provides that:

```ts
// in AuthService.resetPassword
await this.transactions.run(async (tx) => {
  const claimed = await this.tokens.claim(tokenHash, 'PASSWORD_RESET', tx);
  if (!claimed) throw new InvalidTokenError();
  await this.users.applyPasswordReset(claimed.userId, newHash, tx);
});
```

- `tx` is TaskFlow's own small type wrapping TypeORM's transaction manager. Services pass it along but never use it directly.
- Each repository method accepts an optional `tx`. With it, the query joins the transaction; without it, the query runs on its own.
- The runner retries once if MariaDB reports a deadlock.

### How the rule is enforced

- **Lint rule:** ESLint's built-in `no-restricted-imports` forbids importing `typeorm` or `@nestjs/typeorm` anywhere except `*.repository.ts`, `*.entity.ts`, `src/database/**` and test helpers. A service that tries to inject a TypeORM repository or `DataSource` fails the build. No extra package needed.
- **Code review** checks that new queries land in a repository method with a clear name.
- **Testing follows the same split:** repositories get integration tests against real MariaDB; services get unit tests with fake repositories.

## Task ownership

Route guards only prove *who* is asking. Ownership, *whose task this is*, is enforced in the database query itself, so no code path can skip it. Six rules make that hold:

1. **The user ID comes only from the verified JWT**, through `@CurrentUser()`. It is never read from a body, query string or URL. The validation pipe rejects a `userId` field if a client sends one.
2. **Only `TasksRepository` touches the tasks table.** Services never get TypeORM's raw `Repository<Task>`; a lint rule blocks importing it elsewhere.
3. **Every repository method takes `userId` as its first argument** and puts it in the `WHERE` clause: `findActiveOwned(userId, id)`, `listActive(userId, query)`, `countForDashboard(userId, today)`, `moveToTrash(userId, id)`, `findTrashedOwned(userId, id)`, `restore(userId, id)`, `deletePermanently(userId, id)`, `emptyTrash(userId)`. There is no method that finds a task by ID alone.
4. **Changes happen in one statement that includes ownership and location:** for example, set `deletedAt` where `id`, `userId` match and `deletedAt` is null. If zero rows changed, the service returns 404. This is safer than reading first and writing second, because nothing can change in between.
5. **Active versus Trash is part of the query.** Active-task methods only see rows with no `deletedAt` (TypeORM adds this automatically \[D6\], and we state it explicitly anyway). Trash methods only see rows that have one. This is how a permanent delete of an active task returns 404 (AC-20.4).
6. **Responses are built from response DTOs**, so nothing besides the task's own fields ever leaves the API.

**How we prove it:** an automated isolation suite logs in as user A, takes the IDs of user B's active and trashed tasks, and calls every task and Trash endpoint with them. Every call must return 404 and leave B's data unchanged (AC-08.4, AC-19.2, AC-20.5). Lists and counts are checked to contain only A's data. New endpoints are added to this suite in the same pull request.

## Scheduled jobs

One `CleanupService` in `JobsModule` runs once a day through `@nestjs/schedule`, at 21:00 UTC (02:30 in India, a quiet hour). It runs three steps in order:

| Step | Deletes | Rule (checked inside the SQL) | Covers |
| --- | --- | --- | --- |
| Trash purge | Tasks | `deletedAt` is set **and** older than 30 days | FR-TASK-11 |
| Unverified accounts | Users, with their tokens through `ON DELETE CASCADE` | `emailVerifiedAt` is null **and** `createdAt` older than 7 days | FR-AUTH-17 |
| Expired tokens | Auth tokens | `expiresAt` more than 1 day ago | D10 |

Each step is a single repository method (`tasks.purgeTrashedOlderThan(30, 1000)`, `users.deleteUnverifiedOlderThan(7, 1000)`, `tokens.deleteExpiredOlderThan(1, 1000)`), so the job itself contains no SQL (see Repositories).

### Why it's safe to run any number of times

- **The rule is the only selector.** Each step is a single `DELETE` whose `WHERE` clause states the rule. A second run finds nothing new to delete, and a run after a missed day catches up, because the rule says "older than", not "exactly".
- **The rule is checked at the moment of deletion.** A task restored a second before the job runs no longer has `deletedAt`, so the same statement skips it (AC-P.3). Same for an account verified just in time.
- **Times come from MariaDB's clock** (`NOW(3) - INTERVAL 30 DAY`), not the app's, so a clock difference between servers can't change what "30 days" means (G11).
- **Deletes run in batches** of 1,000 rows until none are left, so a large backlog never locks the table for long.
- **No overlap:** if a run is still going when the next one is due, the new one is skipped.
- **One failure doesn't block the others:** each step logs its count or its error, and the next step still runs. Anything missed is caught the next day.

### Later, with more than one server

If TaskFlow ever runs several backend instances, each would run the job. That's harmless, because of idempotency, just wasteful. The fix then is a MariaDB named lock (`GET_LOCK`), so only one instance runs it, with no new technology. This is already listed under Limitations in Requirements v2.

### Testing the jobs

The job methods are ordinary service methods, so integration tests call them directly instead of waiting for the schedule. Tests insert rows with `deletedAt` 31 and 29 days ago, a restored task, an active task, and verified and unverified users of different ages; run the job twice; and check exactly the right rows are gone (AC-P.1 to P.4, AC-C.1 to C.3).

## API

### Conventions

- Every path starts with `/api`. Resources are plural nouns (`/tasks`, `/trash`).
- JSON in and out, field names in camelCase. Timestamps are ISO 8601 strings in UTC; due dates are `YYYY-MM-DD`.
- `201` for a created task, `204` when there's nothing to return, `200` otherwise.
- Every POST, PATCH and DELETE needs the `X-CSRF-Token` header \[D3\].
- Request bodies and query strings are DTO classes validated by class-validator. Responses are built by mapper functions such as `toTaskResponse(task)`, never by returning entities (G6).

### Response shapes

```ts

interface TaskResponse {
  id: string;
  title: string;
  description: string | null;
  priority: 'LOW' | 'MEDIUM' | 'HIGH';
  status: 'PENDING' | 'COMPLETED';

}

  purgeAfter: string;         // deletedAt + 30 days, for the countdown

### Validation rules

| DTO | Field | Rule |
| --- | --- | --- |
| Register | `name` | Trimmed, 1 to 50 characters \[D17\] |
| Register | `email` | Trimmed, lowercased, valid format, at most 254 characters |
| Register, Reset | `password`, `newPassword` | Shared checkPassword: at least 8 characters with a letter and a number; at most 72 UTF-8 bytes; normalized to NFC \[D11, D20, D21\] |
| Login | `email`, `password` | Present only. Login never reveals the password rules. |
| Verify, Check, Reset | `token` | String, at most 128 characters |
| Create task | `title` | Trimmed, 1 to 100 characters; blank gives "Title is required" |
| Create task | `description` | Optional, at most 1,000 characters; empty becomes null |
| Create task | `priority` | Optional `LOW`, `MEDIUM` or `HIGH`; default `MEDIUM` |
| Create task | `dueDate` | Optional; strict `YYYY-MM-DD` and a real calendar date; past dates allowed |
| Update task | all fields | Same rules, all optional, at least one present; `status` is `PENDING` or `COMPLETED`; `dueDate: null` clears it |
| List tasks | `search` | Optional, trimmed, at most 100 characters; `%` and `_` escaped (G4) |
| List tasks | `status` | Optional `PENDING` or `COMPLETED`; absent means All |
| List tasks | `priority` | Optional comma list, e.g. `LOW,HIGH`; each value checked; absent means All |
| List tasks | `sortBy`, `order` | `dueDate`, `createdAt` or `priority`; `asc` or `desc`; default `createdAt desc` \[D12\] |
| List, Trash | `page`, `pageSize` | Whole numbers; page at least 1; pageSize 1 to 50, default 10 |
| Dashboard | `today` | Required, strict `YYYY-MM-DD` |

Any field not listed, such as `userId`, is rejected with 400. An invalid enum value is rejected with 400 and never falls back to unfiltered data (AC-11.8).

Trash is always sorted newest-deleted first, as `deletedAt DESC, createdAt DESC, id DESC`, which matches its index exactly (see Indexes). Lengths are counted in Unicode characters on both sides, the same way MariaDB counts them (R17).

### Errors

| Code | Status | When |
| --- | --- | --- |
| `VALIDATION_FAILED` | 400 | Input breaks a rule; `fields` lists each problem |
| `TOKEN_INVALID`, `TOKEN_EXPIRED` | 400 | Bad verification or reset link |
| `UNAUTHENTICATED` | 401 | No session, expired session or old `tokenVersion` |
| `INVALID_CREDENTIALS` | 401 | Wrong email or password |
| `EMAIL_NOT_VERIFIED` | 403 | Correct password, unverified email |
| `CSRF_INVALID` | 403 | Missing or wrong CSRF token |
| `NOT_FOUND` | 404 | Missing, someone else's, or in the wrong place (active vs Trash) |
| `TOO_MANY_ATTEMPTS` | 429 | Login limit reached |
| `INTERNAL_ERROR` | 500 | Anything unexpected |

**How errors flow:** services throw NestJS exceptions carrying our code, for example `new NotFoundException({ code: 'NOT_FOUND' })`. The validation pipe's error factory turns class-validator results into the `fields` list. `AllExceptionsFilter` turns everything into the `ErrorResponse` shape. Unknown errors become a generic 500; the full stack trace goes only to the server log, tagged with the same `requestId`. A duplicate-email database error from two simultaneous registrations is caught in the auth service and answered with the normal generic message.

## Frontend

### Where each kind of state lives

The most common Redux mistake is copying server data into hand-written slices. Then there are two copies that drift apart, and you write code to keep them in sync. We avoid that by giving each kind of state exactly one home.

| Kind of state | Its one home | Examples |
| --- | --- | --- |
| Data from the server | RTK Query's cache | Tasks, Trash, dashboard counts, the current user |
| List view settings | The URL query string | `/tasks?status=PENDING&priority=HIGH,LOW&sortBy=dueDate&page=2` |
| Form input | React Hook Form | Create and edit task, login, register |
| Short-lived UI | Component state | Is a dialog open |
| Hand-written Redux slices | None at the start | Added only if real client-side state shared across pages appears |

There is no `authSlice`: "who is logged in" is simply the `getMe` query's result. Keeping list settings in the URL means Refresh, Back and shared links show the same view, and "back to page 1 when a filter changes" (FR-ORG-7) is one rule: any change except the page removes `page` from the URL.

### RTK Query setup

- **One `baseApi`** created with `createApi` and `fetchBaseQuery({ baseUrl: '/api' })`. Same origin means cookies are sent automatically.
- **`prepareHeaders`** reads the `tf_csrf` cookie and adds `X-CSRF-Token`.
- **A small wrapper** around the base query handles two cases centrally:
  - 401 on any call except `getMe` and `login`: clear the cache and go to `/login`, remembering where the user was.
  - 403 `CSRF_INVALID`: fetch a fresh CSRF token and retry once.
- **Each feature adds its endpoints** with `injectEndpoints`: `authApi`, `tasksApi`, `trashApi`, `dashboardApi`.
- **Tags** keep data fresh without manual refetching. Each query provides tags; each mutation invalidates the ones it changes:

| Mutation | Invalidates |
| --- | --- |
| `createTask` | task list, dashboard |
| `updateTask` (including status toggle) | that task, task list, dashboard |
| `moveToTrash` | that task, task list, Trash, dashboard |
| `restoreTask` | Trash, task list, dashboard |
| `deletePermanently`, `emptyTrash` | Trash |
| `login`, `logout` | Everything: `resetApiState()` so no previous user's data remains |

- **No optimistic updates.** The list changes only after the server confirms, as approved for deletion (and AC-08.7). Buttons are disabled while a request is in flight to prevent double submits.
- Loading, empty and error states come straight from each query's `isLoading`, data and `error`.

### Forms: React Hook Form with Ant Design

- **React Hook Form owns the form state.** Ant Design's `Form.Item` is used only for layout, labels and showing errors; each input is wrapped in RHF's `Controller`. Letting both libraries manage state would create two sources of truth.
- Rules (`required`, `maxLength`) use the limits from `packages/shared` \[D7\].
- If the server returns `VALIDATION_FAILED`, each entry in `fields` is shown on its input with `setError`.
- A failed save never clears the form, so input isn't lost (US-05 criterion 3).

  limits.ts        NAME_MAX, EMAIL_MAX, TITLE_MAX, DESCRIPTION_MAX,
                   SEARCH_MAX, PAGE_SIZE_DEFAULT, PAGE_SIZE_MAX
  enums.ts         PRIORITIES, STATUSES, TOKEN_TYPES and their types
  validators.ts    checkPassword, utf8ByteLength, normalizePassword,
                   charLength, isIsoDate
  messages.ts      user-facing validation messages
  api-types.ts     TaskResponse, Page, DashboardResponse, ErrorResponse, ...
  error-codes.ts   'NOT_FOUND', 'CSRF_INVALID', ...
```

Only plain TypeScript goes here: no NestJS, React or database code. That keeps it usable by both apps without dragging either framework into the other.

#### Shared code: one source for every limit (R9)

**The rule:** the numbers 50, 100, 1,000 and 72, the enum values and the validation messages appear in exactly one place, `packages/shared`. Backend DTO decorators, entity column lengths and frontend form rules all import them. The only deliberate exception is migrations, which keep literal values as a historical record.

```ts
// Backend: apps/api/src/modules/tasks/dto/create-task.dto.ts
export class CreateTaskDto {
  @Transform(trimString)
  @IsNotEmpty({ message: MESSAGES.TITLE_REQUIRED })
  @MaxChars(LIMITS.TITLE_MAX, { message: MESSAGES.TITLE_TOO_LONG })
  title!: string;

  @IsOptional()
  @MaxChars(LIMITS.DESCRIPTION_MAX, { message: MESSAGES.DESCRIPTION_TOO_LONG })
  description?: string;

  @IsOptional() @IsIn(PRIORITIES)
  priority?: Priority;

  @IsOptional() @IsIsoDate()
  dueDate?: string;
}
```

```tsx
// Frontend: apps/web/src/features/tasks/components/TaskForm.tsx
<Controller
  name="title"
  control={control}
  rules={{
    validate: (v) =>
      v.trim() === '' ? MESSAGES.TITLE_REQUIRED
      : charLength(v) > LIMITS.TITLE_MAX ? MESSAGES.TITLE_TOO_LONG
      : true,
  }}
  render={({ field }) => (
    <Input {...field} count={{ show: true, max: LIMITS.TITLE_MAX, strategy: charLength }} />
  )}
/>
```

- **Counting characters the same way everywhere (R17).** JavaScript's `'😀'.length` is 2, but MariaDB's `VARCHAR(100)` counts it as 1. So both sides use the shared `charLength(s) = [...s].length`. `@MaxChars` is a tiny custom decorator that calls it, and Ant Design's input counter uses it as its counting strategy.
- **`@IsIsoDate`** and **`@IsValidPassword`** are small custom decorators wrapping the shared `isIsoDate` and `checkPassword`.
- **Contract test:** an integration test reads each text column's maximum length from MariaDB's `information_schema` and compares it with `LIMITS`. If someone changes a constant without a migration, or the reverse, the build fails.
- **Build setup:** `packages/shared` is plain TypeScript with no framework imports. M0 sets up how NestJS and Vite consume it, and a smoke test imports it from both apps.

## Testing strategy

Each level of test answers a different question. Fast, narrow tests catch most mistakes; slower, wider tests prove the pieces work together.

| Level | Tool | Question it answers | Runs against |
| --- | --- | --- | --- |
| Unit | Jest | Does this one rule work? | Services and helpers, with repositories replaced by fakes |
| Integration | Jest | Does this query or transaction behave correctly in real MariaDB? | Repositories, transactions and jobs against a real test database |
| API end-to-end | Jest + Supertest | Does the whole API behave as the acceptance criteria say? | The full NestJS app with a real test database and a fake mail service |
| Frontend component | Jest + React Testing Library + MSW \[D13\] | Does this page behave correctly for the user? | Pages and components in a simulated browser, with a faked API |
| Browser end-to-end | Playwright, later \[D14\] | Does a real browser complete a whole journey? | The running app |
| Manual | Postman + Mailpit | Exploration and demos | The running app |

### How tests run

- **A separate MariaDB test database** in Docker Compose. Migrations run once before the suite; tables are emptied between tests. Tests never use SQLite or another stand-in, because MariaDB-specific behaviour (ENUM sorting, collations, DATE handling) is exactly what we need to test.
- **A fake mail service** replaces SMTP in automated tests and records each email, so a test can read the verification link directly. Mailpit is for manual testing.
- **Coverage target:** at least 70% on backend services (from the Phase 1 non-functional requirements), and every task and Trash endpoint in the isolation suite.
- **GitHub Actions** runs lint, type checks, unit, integration and API end-to-end tests on every pull request, with MariaDB as a service container. A pull request can't merge while anything fails.
- **Postman collection** in `docs/postman/`, with a pre-request script that copies the CSRF cookie into the header.

### Test environment details

- **`TextEncoder` in frontend tests (R16):** Jest's browser-like environment may not provide `TextEncoder`, which the shared byte counter uses. A one-line test setup file assigns Node's own `TextEncoder` to the test environment. No package needed.
- **Time zones:** tests normally run with `TZ=UTC`. The date tests also run under `Asia/Kolkata` and `America/Los_Angeles` (see Date-only values).
- **Clock:** the rate limiter and token expiry use an injected clock, so tests move time forward instead of waiting.

### Performance test (R11)

The requirement: the task list API responds in under 500 ms for a user with 1,000 tasks. We don't assume an index helps contains-search; we measure.

**Why no index helps the search itself:** a B-tree index is sorted from the first character, like a phone book. It can find names *starting* with "Rep", but not names *containing* "rep" somewhere in the middle. A `LIKE '%rep%'` search must check every candidate row. What our index does is narrow the candidates to one user's active tasks, at most about 1,000, before the text check starts.

**Dataset:** a seed script creates the test user with 1,000 active and 200 trashed tasks, with realistic title and description lengths (including some full 1,000-character descriptions), mixed priorities, statuses and due dates. It also creates 20 other users with 1,000 tasks each, so the table holds about 21,000 rows. Without other users' rows, a missing index would go unnoticed.

**Requests measured,** each through the real HTTP API with Supertest, including authentication, validation and JSON serialization:

- Default list, first page and last page
- Search for a common word, a rare word and a word that matches nothing, each with every sort order
- Status filter plus multiple priorities plus search, together
- Due-date sort (the sort-step case)
- Dashboard counts

**Method:** 5 warm-up requests, then 30 timed requests per case. We report the median and the 95th percentile; **the 95th percentile must be under 500 ms**. Alongside, `ANALYZE FORMAT=JSON` for each underlying query confirms the rows examined never exceed the user's own rows, so the result holds for the right reason.

**Where it runs:** `npm run test:perf` against the Docker MariaDB, in M5 and again in M8, and on demand in CI. It is not part of every pull request, because timings on shared CI machines vary too much to gate merges. Results are recorded in `docs/db/query-plans.md`.

**If it fails:** first check the plan. If the search scan itself is the cost, the planned next step is a MariaDB `FULLTEXT` index, listed under later improvements.

## Essential now vs later

### Essential from the first release

Leaving any of these out would break an approved requirement or open a real security hole.

- **Sessions and CSRF:** httpOnly `__Host-` session cookie; signed, user-bound `__Host-` CSRF token with constant-time checks and the rotation rules; same origin; security headers
- **Authentication:** global auth guard with the `tokenVersion` check; validation pipe that rejects unknown fields and never echoes values
- **Passwords:** shared byte-accurate validation with NFC normalization; over-length logins rejected
- **Tokens:** one row per user and type with atomic replacement; single-statement claims; reset in one transaction with emails after commit
- **Logs:** no bodies, query strings, headers, links or SQL parameters; `redact()` safety net; fragment cleared from the address bar; sensitive mutations reset; DevTools off in production
- **Rate limits:** sliding windows, reservation before the password check, sweep and memory cap, correct `trust proxy`
- **Data access:** all queries in repositories, enforced by lint; ownership in every task query, plus the isolation suite
- **Database:** migrations only, schema drift check, explicit collations, native UUIDs on both sides of every foreign key, UTC everywhere, `dateStrings` for `DATE`, the reviewed index set
- **Shared limits:** one source in `packages/shared`, the contract test, character counting matched to MariaDB
- **Jobs:** idempotent, batched, using the database clock, through repositories
- **Testing:** API end-to-end and integration tests against real MariaDB; the performance test in M5 and M8; CI on every pull request

### Can wait, with a known path

| Improvement | Add it when | How |
| --- | --- | --- |
| Redis for rate limits | A second backend instance is added | Swap the store behind the rate-limit interface |
| Single-runner jobs | A second backend instance is added | MariaDB `GET_LOCK` around the cleanup |
| Rate-limit keys by IPv6 network | Attackers rotate IPv6 addresses | Group IPv6 addresses by their /64 network in the key |
| Automated query-plan checks | Query plans start drifting between releases | Assert expected index and row counts from `ANALYZE` in the performance suite |
| Due-date sort without a sort step | The performance test shows the sort as the bottleneck | Add a generated "has due date" column and include it in an index |
| Full-text search | Search exceeds the 500 ms target | MariaDB `FULLTEXT` index |
| Time-ordered IDs (UUID version 7) | Task tables grow very large | Newer UUIDs sort by creation time, so inserts land at the end of indexes |
| Refresh tokens | Hourly re-login becomes annoying | Short access tokens plus refresh tokens, revoked on reset (FR-AUTH-14) |
| "Log out of all devices" | Users ask for it | Increment `tokenVersion` on request |
| Browser end-to-end tests | The core journeys are stable | Playwright for register, create, Trash and reset journeys \[D14\] |
| API documentation | Other people consume the API | `@nestjs/swagger` generates docs from the existing DTOs |
| Centralised logging and alerts | The app is in production | Ship the existing redacted structured logs to a hosted service |
| Request timeouts | Slow dependencies appear | A timeout interceptor |
| MariaDB upgrade | Before 11.4's support ends in May 2029 | Move to the then-current LTS release |

## Implementation sequence

We build in **vertical slices**: each milestone delivers one feature through the database, the API, the frontend and the tests, so you can use it in the browser before moving on. Building the whole backend first would delay the first thing you can see by weeks and hide integration mistakes until late.

**Git workflow for every milestone:** a branch named after it (for example `m4-tasks`), small commits that mention requirement IDs (`FR-TASK-4: move task to Trash`), a pull request that CI must pass, then a review together before merging.

1. **M0 Foundation.** Monorepo with npm workspaces; strict TypeScript, ESLint and Prettier, including the rule that keeps TypeORM imports inside repositories; `packages/shared` wired into both apps with a smoke test; Docker Compose with MariaDB 11.4, a test database and Mailpit; `TZ=UTC` everywhere; NestJS app with validated config, helmet, global validation pipe (values never echoed), exception filter, logging interceptor with `redact()`, and `GET /api/health`; Vite app with Ant Design, Redux store and `baseApi`, with the `/api` proxy; Jest setup including the `TextEncoder` line; GitHub Actions running lint and tests.
   - *Why first:* every later milestone stands on it, and it proves browser, API, shared code and database work together.
2. **M1 Database foundation.** The three entities with explicit UUID types; the reviewed first migration; the schema drift check in CI; `TransactionRunner`; repository skeletons; seed script. Tests: UUID integration test, date-only round trips under three time zones, the shared-limits contract test.
   - *Why now:* these tests prove the riskiest database choices (native UUIDs, dates, collations) before any feature depends on them.
3. **M2 Register, verify, log in, log out.** `TokensRepository` with atomic issue and claim; mail module with Mailpit and the test fake; session cookie; signed CSRF tokens with rotation; global auth guard with `tokenVersion`; shared password validation; login with attempt reservation; the rate limiter. Frontend: auth pages, the verify page clearing its fragment, `getMe`, route guards. Tests: password boundary list in both suites, every rate-limiter scenario, CSRF cases, parallel resend requests, log redaction.
   - *Why before tasks:* every task endpoint needs a logged-in user, and security code is easiest to get right on its own.
4. **M3 Password reset.** Forgot, check and reset endpoints; claim and reset in one transaction; password-changed email; the reset page clearing its fragment. Tests: parallel reset submissions and requests, rollback (AC-17.11), old session 401 and fresh login (AC-17.5, AC-17.9), redaction across reset failures.
5. **M4 Tasks.** `TasksRepository` with ownership on every method; create, view, edit, toggle, move to Trash; task list (no filters yet), details and form pages using shared limits and `charLength`; **the isolation suite**.
   - *Why the isolation suite now:* it is the most important test in the project, and every later endpoint joins it.
6. **M5 Search, filters, sort and pagination.** Query DTO and validation; LIKE escaping; tie-breakers; empty due dates last; URL-driven filters and debounced search. The performance dataset and `npm run test:perf`; query plans for list, search and sorts recorded in `docs/db/query-plans.md`.
7. **M6 Trash and cleanup.** Trash endpoints and page, sorted to match the index; confirmation and toast wording; the daily cleanup job's three repository steps with idempotency tests; query plans for Trash and cleanup queries recorded.
8. **M7 Dashboard.** One counting query using the covering index, with the `today` parameter; dashboard page and empty state; its query plan recorded.
9. **M8 Hardening.** Every page at 360 px; loading, empty and error states; security headers verified; performance test re-run; logs reviewed for sensitive data; coverage measured; Postman collection completed; every acceptance criterion walked through end to end; optional Playwright journeys \[D14\].

In each milestone we keep the same rhythm: read the requirements it covers, write tests from their acceptance criteria, build until they pass, then review the code together.
